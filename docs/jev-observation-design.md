# Logging · Monitoring JEV 적용 설계

작성일: 2026-10-02. **구현 전 설계안**이며 아래 신규 API·설정·패키지는 아직 존재하지 않는다.

## 1. 적용 범위와 역할

JEV는 관측 자료에서 제한된 선택지를 판정한다. observer는 근거 수집과 규칙 판정,
builder는 JEV 호출과 응답 검증, CI/CD는 배포 상태와 트래픽 변경을 맡는다.
우선 적용 순서는 **장애 사전 분류 → 카나리 판정 → 트래픽 이상 분류**다.

| 단계 (담당) | JEV에 묻는 것 | 서버 정책으로 바뀌는 것 | 이번 구성 |
|---|---|---|---|
| 빌드 실패 (박준석·이현수) | 의존성/컴파일/테스트/네트워크/메모리 부족, 그대로 재시도 가능한가 | 재시도 1회 / 수정 PR 경로 / 사람 호출 | CI/CD·builder 확장 |
| DB 마이그레이션 (이현수·박준석) | 확장/축소/데이터 이전/잠금 위험, 구버전 호환성 | 적용 / 구버전 종료 후 적용 / 승인 요청 | CI/CD 확장 |
| 카나리 (심형규·최도일) | 승격/유지/롤백/판단 불가 | **규칙 통과 구간에서만 승격 보류 여부** | 2차 MVP |
| 장애 사전 분류 (Logging) | DB/업스트림/자원/코드 등 원인 후보와 P0~P4 | P0·P1만 상세 LLM 장애 분석 큐로 전달 | 1차 MVP |
| AI 수정 PR 검증 | 문제 해결 여부, 범위 밖 변경 여부 | 자동 머지 후보 / 사람 검토 라벨 | 후속 확장 |
| 배포 방식 (CI/CD) | 변경 위험도 | 즉시/카나리/블루그린 및 승인자 | 후속 확장 |
| 트래픽 급증 (이도현·차주혜) | 정상 증가/비정상 트래픽/특정 경로 장애 | 스케일 아웃 / 요청 제한 / 알림 | 추가 관측 필요 |

표의 조치들은 목표 정책이다. JEV 답 하나만으로 재시도·마이그레이션·머지·스케일 변경을 실행하지 않는다.
각 담당 모듈이 허용 조건과 승인 정책을 검증한 뒤 실행한다.

## 2. 현재 코드에서 재사용할 것

| 현재 구현 | 재사용 / 확장 지점 |
|---|---|
| `diagnosis/DiagnosisCollector` | 지표·파드·로그·배포 근거 수집, 마스킹. 재사용하되 문자열 요약 외에 구조화된 관측값 추가 |
| `diagnosis/DiagnosisClient` | builder `/api/diagnoses` 호출, 허용 후보·근거 ID 검증 패턴 |
| `diagnosis/DiagnosisService` | 앱별 동시 요청 병합, 성공 30초/실패 5초 캐시, 작업 최대 4개 |
| `judge/RuleBasedRiskJudge` | 요청량·5xx·지연 기반 위험도 규칙. P0~P4 및 카나리 PASS/FAIL과는 별도 개념 |
| `remediate/RemediateWatch` | 기본 `default` namespace, 30초마다 앱 관측, CRITICAL 연속 2회 시 전송 시도 |
| `remediate/StackJoiner` | 같은 파드·같은 시각의 스택 줄 결합. 전체 오류 그룹·빈도 계산 기능은 추가 필요 |
| `remediate/IncidentDraft` | 레포 내 스택 프레임을 가진 코드 사고 초안. 최신 후보 하나를 고르는 기능 |
| `remediate/RemediateSender` | frontend `/api/internal/remediate`로 코드 사고 전달. 일반 장애 분석 큐로 쓰기에는 계약 확장 필요 |
| `watch/Watch`, `WatchState` | 배포 감시 모델만 존재. 배포 등록 API·카나리 실행 루프는 미구현 |

기존 `POST /api/apps/{app}/diagnosis`는 원인 후보와 검토 조치를 반환한다.
자유 형식의 상세 LLM 장애 분석과 동일한 기능으로 취급하지 않는다.
기존 builder 진단도 JEV `choice`와 고정 템플릿을 사용한다.

현재 부족한 자료:

- 지표는 `{app}-ingress`의 앱 전체 합계다. stable/canary 또는 blue/green을 분리하지 못한다.
- `ClusterSource`는 파드 현재 상태만 제공한다. Kubernetes Event 목록과 이벤트 발생 시각은 수집하지 않는다.
- 파드 CPU·메모리는 절대 사용량이다. limits·requests·CPU throttling·종료 시각은 수집하지 않는다.
- 최근 로그 표본은 장애 발생 총량이 아니다. 조회 한도 초과·누락을 함께 표현해야 한다.
- 현재 배포 이미지·슬롯은 배포 변경 이력이 아니다. 배포 ID와 버전 불변 식별자도 연결해야 한다.

## 3. 전체 흐름

```text
CloudWatch 로그 ─┐
Prometheus 지표 ─┼→ observer: 수집 → 마스킹 → 오류 그룹 → 규칙 기반 영향도
파드 / 이벤트 ──┤                                      │
배포 식별 정보 ─┘                                      ▼
                                  builder: JEV 제한 선택 → 검증
                                                       │
                                                       ▼
                                  observer: 규칙 + JEV 결과 → 정책
                                     ├ P0/P1 → 상세 장애 분석 큐
                                     ├ P2~P4 → 기록 / 대시보드
                                     └ 판단 불가 → 영향도 규칙 + 사람 검토

CI/CD: 카나리 검사 → 규칙 FAIL ─────────────→ 기존 실패 처리
                  → 규칙 HOLD ─────────────→ 관측 연장 / 만료 처리
                  → 규칙 PASS → observer/builder/JEV → 승격 또는 제한된 보류
```

JEV 키는 기존과 같이 builder에만 둔다. 관측 대시보드의 `GET /status`마다 JEV를 호출하지 않는다.
일반 로그 한 줄이나 사용자 요청마다 호출하지 않고, 집계된 장애 사건 또는 승격 직전에 호출한다.

## 4. 1차 MVP: 장애 사전 분류

### 입력 구성

1. 지표·파드·배포 관측을 먼저 수집하고 규칙으로 영향도를 계산한다.
2. 설정된 비밀값 패턴을 마스킹한 뒤 스택을 결합한다.
3. `(namespace, app, deploymentId, exceptionType, firstAppFrame)`로 오류를 묶는다.
   프레임이 없으면 파드 문제/이벤트 reason과 정규화된 메시지를 이용한다.
4. 각 그룹의 대표 표본, 관측 구간, 조회된 발생 건수, 최초/최종 시각과 누락 여부를 구성한다.
   UUID·요청 ID·시각처럼 변하는 부분은 정규화하되 SQLSTATE·HTTP 상태·경로 정보는 보존한다.
5. 원인 신호가 있거나 영향도가 높을 때만 builder에 분류를 요청한다.

1차는 기존 로그·파드 상태를 사용하고 `events`는 미수집으로 명시한다.
2차에서 Event UID·reason·message·발생 시각·대상 Pod UID를 추가한다.
이벤트와 과거 OOM 종료는 이번 관측 구간과 연관될 때만 현재 장애의 근거로 사용한다.

### JEV 질문과 선택지

| 질문 | 허용 선택지 | 판정 제약 |
|---|---|---|
| 어떤 원인 후보가 근거에 맞는가 | `database`, `upstream`, `resources`, `application`, `configuration`, `unknown` | 근거 없는 후보는 선택지에서 제외. `unknown`은 항상 포함 |
| 어느 우선순위로 다뤄야 하는가 | `P0`, `P1`, `P2`, `P3`, `P4`, `unknown` | 영향 범위·지속 시간·실패량이 부족하면 보류 |

현재 JEV 클라이언트는 질문 하나를 처리하므로 기본은 원인·우선순위 최대 2회 호출이다.
하나가 실패해도 다른 결과는 보존한다. 질문마다 허용 선택지, 유한한 확신도, 최소 0.8을 검증한다.
복합 선택지로 합치는 최적화는 이후 실제 판정 품질을 보고 결정한다.
두 질문과 관측을 합친 전체 제한 시간을 두며 질문별 타임아웃을 더해 무한 연장하지 않는다.
작업 수·대기열을 제한하고 주기 감시 스레드에서 외부 호출을 기다리지 않는다.
기존 상태 감시는 계속 수행하고 분류 작업이 밀리면 그 상태를 별도로 기록한다.

아래는 우선순위 정의 **초안**이다. 코드의 `RiskLevel`과 일대일로 매핑하지 않는다.

| 우선순위 | 의미 | 판정에 필요한 근거 |
|---|---|---|
| P0 | 플랫폼 다수 앱 장애 또는 확인된 데이터 손실 | 여러 앱·핵심 기능 영향 또는 별도 데이터 무결성 신호 |
| P1 | 한 앱의 핵심 기능이 지속적으로 이용 불가 | 충분한 요청량, 지속 실패, 핵심 경로 또는 Ready 부재 |
| P2 | 일부 기능 저하, 우회 가능 | 부분 실패·지연·재시작과 제한된 영향 범위 |
| P3 | 일시적 오류, 사용자 영향 작음 | 짧은 발생 구간과 회복 근거 |
| P4 | 정보성/중복/조치 불필요 | 이미 처리된 동일 사건 또는 비장애 근거 |

앱 한 개의 예외 로그만으로 P0나 핵심 기능 장애를 확정하지 않는다.
핵심 경로 정의와 우선순위 임계치는 팀 정책으로 설정하며, 설정되지 않은 항목은 `unknown`을 허용한다.

### 판정을 후속 처리로 바꾸는 정책

숫자가 작을수록 긴급하다. 최종 우선순위는 규칙과 유효한 JEV 결과 중 더 긴급한 것을 사용한다.
JEV가 규칙의 P0/P1을 P2 이하로 내릴 수 없다.

| 상황 | 최종 처리 |
|---|---|
| 최종 P0/P1 + 분석 큐 연결 활성화 | 근거와 함께 상세 LLM 분석 큐에 전달. 알림은 분석 완료를 기다리지 않음 |
| 최종 P2~P4 | 분류 기록과 대시보드 표시. 자동 상세 분석 호출 생략 |
| JEV 실패/저확신/잘못된 선택 | 규칙 우선순위 유지, 원인 `unknown` 허용 |
| 규칙과 JEV 모두 우선순위 판단 불가 | `needs_review`와 경량 알림. 자동 상세 분석은 생략 |
| 분석 전송 실패 | 사건 보존, 같은 사건 ID로 제한된 재시도. 전달 성공 후에만 완료 처리 |

**상세 분석과 코드 수정은 분리한다.** DB/업스트림/자원 장애도 P0/P1이면 분석 대상이다.
수정 PR 경로는 상세 분석 후 코드 원인과 배포 커밋·레포 프레임이 확인된 경우에 연결한다.
기존 `IncidentDraft`가 프레임 없는 사고를 거절하는 동작을 일반 장애 분석의 진입 조건으로 사용하지 않는다.

장애 트리거는 CRITICAL 연속 조건뿐 아니라 새로운 CrashLoop/OOM, Ready 부재도 고려한다.
낮은 요청량으로 규칙이 HOLD가 되는 장애를 놓치지 않기 위해서다.
누적 재시작 횟수가 아니라 이전 관측 대비 증가·발생 시각으로 새 사건을 판정한다.

### 중복·캐시·수명

- 사건 키는 namespace/app/deploymentId/fingerprint. 재배포 후 동일 예외를 이전 사건으로 덮지 않는다.
- 관측 스냅샷 해시와 정책 버전이 같은 분류만 재사용한다. 영향도가 상승하면 새 분류를 수행한다.
- 한 사건의 반복 전송은 합치되 P2→P1 상승, 새로운 배포, 회복 후 재발은 별도 전달한다.
- 기존 앱별 진단 캐시는 그대로 재사용하지 않는다. 서로 다른 그룹과 배포가 섞일 수 있다.
- 자동 연결 단계에서는 사건·전송 상태를 저장할 저장소가 필요하다. 메모리만 쓰는 초기 구현은
  프로세스 재시작과 여러 replica 사이의 중복 방지를 보장하지 않음을 명시한다.

## 5. 2차 MVP: 카나리 승격 보류

### 관측 경계

CI/CD가 배포 ID, 후보/기준 이미지 digest, 슬롯, 검사 시작·종료 시각,
후보/기준 요청 수·5xx·지연·규칙 판정을 observer에 전달한다.
observer는 그 구간과 슬롯에 해당하는 로그·파드 근거를 추가한다.
앱 전체 ingress 지표를 후보 버전 지표로 해석하지 않는다.

당장은 CI/CD의 버전별 검사 결과를 사용하고, 향후 슬롯별 메트릭 출처가 확인되면 직접 수집을 확장한다.
기존 30초 검사 안에 관측·JEV 호출 시간을 억지로 포함하지 않고 별도 제한 시간을 합의한다.
증거가 후보 배포·검사 구간과 연결되지 않으면 `insufficient_evidence`로 취급한다.

### 권한과 결정표

JEV 선택지는 `promote`, `hold`, `rollback`, `unknown`이지만 실행 효과는 아래로 제한한다.
JEV의 `rollback`은 PASS 상황에서 **승격 보류 및 사람 검토**로만 변환한다.

| 규칙 | JEV | observer 반환 | CI/CD 처리 |
|---|---|---|---|
| FAIL | 호출 안 함 | `rule_failed` | 기존 실패/복구 처리 유지 |
| HOLD / 자료 부족 | 호출 안 함 | `await_observation` | 관측 연장, 만료 시 기존 종료 정책 |
| PASS | promote | `allow_promotion` | 배포 ID·버전 일치 확인 후 승격 |
| PASS | hold / rollback | `hold_promotion` | 승격 보류, 재관측 또는 사람 검토 |
| PASS | unknown / 타임아웃 / 검증 실패 | shadow에서는 `record_only`, 강제 적용에서는 `hold_promotion` | 강제 적용 시 제한 시간까지만 보류 |

보류 만료 시 자동 승격하지 않는 것을 강제 적용 기본안으로 한다.
CI/CD가 기존 버전을 유지하고 후보 배포를 종료하거나 담당자에게 넘긴다.
보류 최대 시간·재관측 횟수는 설정값으로 확정하고 무한 대기하지 않는다.
첫 배포·기준 슬롯 부재는 카나리 비교 대상에서 제외해 기존 배포 정책으로 처리한다.

응답에 `deploymentId`, 후보 digest, `snapshotId`, `policyVersion`, `expiresAt`을 포함한다.
CI/CD는 새 배포로 교체되었거나 만료된 판정을 무시한다. 최종 상태 전환은 CI/CD가 한 번만 수행한다.

기존 `lily-jev/README.md`의 “CRITICAL을 확실한 잡음이면 WARNING으로 내리기”는 이전 구상이다.
이 설계에서는 위험 규칙을 낮추지 않고 **통과한 배포의 승격 보류만** 추가한다.

## 6. 제안 연동 계약

기존 `/diagnosis` 응답은 유지한다. 분류와 승격은 별도 계약으로 추가한다.
아래 경로는 협의용이며 아직 라우팅·인증 필터에 등록되어 있지 않다.

| 호출자 → 수신자 | 신규 경로 | 목적 |
|---|---|---|
| 인증된 내부 서버 → observer | `POST /api/apps/{app}/triage?namespace=...` | 서버가 직접 수집한 장애의 사전 분류 조회 |
| CI/CD → observer | `POST /api/canary-assessments` | 배포별 규칙 검사 결과에 승격 보류 판정 추가 |
| observer → builder | `POST /api/observation-decisions` | 유형별 JEV 질문과 검증 |
| observer → 상세 분석 담당 서비스 | 경로 미정 | P0/P1 사건의 비동기 분석 요청 |

builder 요청 골격:

```json
{
  "schemaVersion": "1",
  "kind": "incident_triage",
  "requestId": "decision-123",
  "snapshotId": "snapshot-123",
  "policyVersion": "triage-v1",
  "app": "blog",
  "namespace": "default",
  "deploymentId": "deploy-123",
  "observedAt": "2026-10-02T00:00:00Z",
  "window": {"from": "2026-10-01T23:59:00Z", "to": "2026-10-02T00:00:00Z"},
  "ruleAssessment": {"priority": "P1", "reasonCode": "sustained_core_path_failure"},
  "evidence": [
    {"id": "log-1", "source": "logs", "signal": "database_error", "summary": "SQLSTATE 08006"},
    {"id": "metrics-1", "source": "metrics", "signal": "high_error_rate", "summary": "core path failure in window"}
  ],
  "missingSources": ["events"]
}
```

구현 시 `ruleAssessment`의 수치·지속 시간·경로별 실패량은 타입이 있는 필드로 정의한다.
요약 문장만으로 우선순위를 판정하지 않는다.

분류 결과 골격:

```json
{
  "requestId": "decision-123",
  "snapshotId": "snapshot-123",
  "deploymentId": "deploy-123",
  "policyVersion": "triage-v1",
  "category": {"value": "database", "source": "jev", "evidenceIds": ["log-1"]},
  "priority": {"value": "P1", "source": "rules", "evidenceIds": ["metrics-1"]},
  "state": "classified",
  "limitations": ["events_missing"]
}
```

두 판정의 출처를 각각 남긴다. 기존 diagnosis의 `source: ai`와 신규 계약의 `source: jev`는
버전이 다른 필드이므로 기존 응답을 바꾸지 않는다.
최종 `route: deep_analysis | record_only | needs_review`는 observer 정책이 계산한다.
JEV가 후속 서비스 주소, 실행 명령, 파일 경로나 자유 형식 조치를 지정하지 못한다.

계약 검증 항목:

- 종류별 enum·필수 필드·입력 개수·전체 본문 크기 제한과 허용 근거 ID.
- 요청 ID·배포 ID·스냅샷·정책 버전 일치 및 카나리 응답 만료 시각.
- 누락 자료는 누락으로 유지. 빈 지표를 정상으로 판정하지 않음.
- 기존 DNS label 검증과 내부 Bearer 인증. 신규 builder 경로에도 인증 필터를 확장해야 함.
  현재 builder의 `DiagnosisTokenFilter`는 `/api/diagnoses`만 대상으로 한다.
- 기존 builder는 `events`, `upstream_error` 등을 허용하지 않으므로 새 계약에서 별도로 정의.
- 마스킹 후 전송, 로그는 신뢰하지 않는 자료로 취급. 설명·조치·근거 연결은 서버가 생성.

## 7. 구현 단위와 도입 순서

| 순서 | observer | builder / 다른 모듈 | 완료 기준 |
|---|---|---|---|
| 1. 사전 분류 조회 | `triage/`의 관측 모델·그룹화·정책·내부 API | 신규 분류 계약과 JEV 질문 | 모의 응답으로 원인·우선순위·보류 검증 |
| 2. 자동 분류 관찰 | 별도 watch에서 영향도 변화·파드 장애 감지, 판정 저장 | 아직 분석 전송 생략 | 기존 판정과 JEV 차이 및 호출량 측정 |
| 3. P0/P1 전달 | 사건 저장·중복 병합·전송 상태 | 상세 분석 큐 계약, 소유 서비스 결정 | P0/P1만 전달, 실패 재시도와 알림 독립 확인 |
| 4. 카나리 관찰 | `canary/`의 근거 연결·정책·응답 검증 | CI/CD 검사 결과와 배포 식별 계약 | 규칙 통과 상황의 보류 제안을 기록 |
| 5. 카나리 강제 적용 | 만료·대체 배포 처리 | CI/CD 보류 상태와 종료 정책 | 실패 규칙 우회 없음, 오래된 결과 적용 없음 |
| 6. 트래픽 분류 | 경로별 지표·용량·유입 패턴 확장 | LB 제한·스케일 정책 | 원인별 근거 확보 후 실행 연동 |

설정은 분류 활성화, 자동 분류, 상세 분석 전송, 카나리 관찰/강제 적용을 각각 분리한다.
모든 신규 기능은 기본 꺼짐으로 시작한다. 기존 remediate 전송은 신규 분류 흐름으로 전환할 때
중복 전달을 막도록 명시적으로 교체한다. 별도 모드를 동시에 켜지 않는다.

검증할 핵심 사례:

- DB 장애 P1은 코드 프레임 없이도 상세 분석 대상이며, 수정 PR은 자동 요청하지 않는다.
- 규칙 P1 + JEV P3은 최종 P1. 자료 부족은 정상이나 P4로 바뀌지 않는다.
- 저트래픽 + 새 CrashLoop는 분류 대상. 오래된 OOM 사유만으로 현재 P1을 만들지 않는다.
- 카나리 FAIL + JEV promote는 승격 불가. PASS + hold/rollback은 보류만 가능.
- JEV 장애·낮은 확신·잘못된 근거 ID는 규칙 유지 또는 제한된 보류로 처리한다.
- 배포 교체·응답 만료·전송 실패·프로세스 재시작에도 잘못된 배포를 처리하지 않는다.

팀이 확정할 정책은 핵심 경로 정의, P0/P1 임계치·지속 시간, 상세 분석 큐 담당,
카나리 보류 최대 시간과 만료 처리다. 이 값들은 JEV 프롬프트가 아니라 버전 관리되는 서버 정책으로 둔다.
