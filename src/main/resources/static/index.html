lily-observer API

배포된 앱의 상태 · 지표 · 파드 · 로그 · 서버 정보를 조회합니다. 대시보드와 AI 진단이 이 API를 씁니다.

Swagger UI OpenAPI 명세 (JSON)
대시보드 연동 가이드 API 한눈에 앱 목록 패널 상태 요청 지표 파드 상태 로그 서버 다른 앱 지원 범위 위험도 기준 에러 응답

토큰

이 페이지의 "직접 호출"에만 씁니다. 서버에 OBSERVABILITY_API_TOKEN이 없으면 비워 두세요. 탭을 닫으면 지워집니다.

대시보드 연동 가이드

lily-frontend에서 꽃을 누르면 DASHBOARD_URL?project={id}로 이동합니다. 대시보드는 이 API로 앱 상태를 보여줍니다.

1. 어디서 호출하나요

상황주소비고
대시보드 서버 (클러스터 안)http://lily-observer.lily-system.svc운영. 같은 k3s 클러스터 안의 서버에서만 닿습니다
로컬 개발http://localhost:8095아래 터널 명령. 이 페이지와 Swagger도 같은 주소
# 내 노트북
ssh -i ~/.ssh/lily-key.pem -L 8095:localhost:8095 ubuntu@43.200.152.53
# 서버 (이 창은 켜둔다)
sudo kubectl -n lily-system port-forward svc/lily-observer 8095:80
  • 브라우저에서 직접 부르지 마세요. 클러스터 안에서만 열려 있고(ClusterIP), CORS를 허용하지 않고, 토큰이 노출됩니다.
  • 대시보드 서버(Next.js Route Handler 등)가 대신 부르고, 브라우저는 대시보드 서버만 부릅니다.

2. 타입 자동 생성

OpenAPI 명세에서 TypeScript 타입을 바로 만들 수 있습니다 (터널이 켜진 상태).

npx openapi-typescript http://localhost:8095/v3/api-docs -o src/lib/observer/schema.d.ts

// 사용
import type { components } from "@/lib/observer/schema";
type AppStatus = components["schemas"]["AppStatus"];

3. 앱 이름

  • 경로의 {app}은 배포할 때 쓴 앱 이름입니다 (lily-builder · lily-cicd의 appName). 예: lily-test, book-club-backend-8633c2
  • 접속 주소 https://{app}.apps.lilycloud.kr의 앞부분과 같습니다. GET /api/apps 목록의 app 값을 그대로 쓰면 됩니다.
  • 대시보드는 ?project={id}만 받으므로 프로젝트 → 앱 이름은 lily-frontend의 프로젝트 · 배포 기록에서 찾습니다.
  • namespace는 모든 사용자 앱이 default라 생략합니다.

4. 인증 · 환경변수

OBSERVER_URL=http://lily-observer.lily-system.svc
OBSERVER_TOKEN=...   # lily-observer 의 OBSERVABILITY_API_TOKEN. 아직 미설정(인증 꺼짐)

요청마다 Authorization: Bearer {OBSERVER_TOKEN}. 토큰이 설정되기 전에는 없어도 됩니다.

5. 호출 예시 (Next.js Route Handler, 모든 API 공용 프록시)

// app/api/observer/[...path]/route.ts
export async function GET(req: Request, { params }: { params: Promise<{ path: string[] }> }) {
  const { path } = await params;
  const search = new URL(req.url).search;            // ?window=30m 등 그대로 전달
  const res = await fetch(`${process.env.OBSERVER_URL}/api/${path.map(encodeURIComponent).join("/")}${search}`, {
    headers: process.env.OBSERVER_TOKEN ? { Authorization: `Bearer ${process.env.OBSERVER_TOKEN}` } : {},
    cache: "no-store",
  });
  return new Response(await res.text(), {
    status: res.status,
    headers: { "Content-Type": "application/json" },
  });
}

// 브라우저: fetch("/api/observer/apps/lily-test/status")

8. 표시 팁

  • 모든 시각은 UTC입니다. 화면에는 KST로: new Date(at).toLocaleString("ko-KR", { timeZone: "Asia/Seoul" })
  • 에러율: (errorRate * 100).toFixed(1) + "%". 응답 시간: Math.round(ms) + "ms"
  • series는 오래된 순, 30초 간격. window=30m이면 점 약 60개
  • 로그 message는 길 수 있습니다. 목록에서는 한 줄로 자르고 펼치면 전체

GET/api/apps/{app}/status구현 · MON-05

    
최근 1분 지표를 판정 규칙(자동 롤백과 같은 기준)에 넣어 패널 색과 문구를 돌려줍니다. 화면은 color와 message를 그대로 쓰면 됩니다.

    

      
필드타입뜻

      
level문자열HOLD · NORMAL · NOTICE · WARNING · CRITICAL

      
score-1 ~ 3-1 보류, 0 정상, 1 알림, 2 주의, 3 위험

      
color문자열gray · green · yellow · red

      
action문자열규칙상 조치: 판정 보류 · 없음 · 알림 · 주의 알림 · 롤백

      
message문자열화면에 그대로 보여줄 한 줄. 예: 위험: 에러율 6.2%. 이전 버전으로 되돌리는 것을 권장해요

      
reason문자열판정 근거. 예: 5xx 6.2% ≥ 5.0%, p95 응답 400ms ≥ 기준 150ms x 2.0

      
currentTrafficMetrics최근 1분 (아래 요청 지표와 같은 모양)

      
baselineTrafficMetrics비교 기준: 15분 전 ~ 5분 전. 응답 시간이 이것의 2배를 넘으면 주의

      
judgedAt시각 (UTC)판정 시각

GET/api/apps/{app}/metrics구현 · MON-04

    
앱의 최근 1분 요약(카드)과 30초 간격 추이(그래프)입니다. 앱이 아니라 입구(ingress-nginx)에서 세기 때문에 앱 언어와 상관없습니다.

    
파라미터

    

      
이름기본값설명

      
window10m추이 구간. 1분 ~ 6시간 (Prometheus 보관 1일)

    

    
지표 하나하나

    

      
지표단위계산읽는 법

      
requestsPerMinute회/분요청 수의 최근 1분 증가량응답 코드 무관 모든 요청. 소수점은 15초 간격 숫자로 추정해서 생김. 20 미만이면 판정 보류

      
errorRate0.0 ~ 1.05xx 응답 ÷ 전체 요청0.05 = 5%. 4xx(잘못된 주소 · 권한 없음)는 사용자 쪽 문제라 제외. 기준 1% · 2% · 5%

      
avgLatencyMsms응답 시간 합 ÷ 요청 수ingress가 요청을 받은 순간부터 응답을 다 보낼 때까지. 느린 요청 몇 개는 묻힐 수 있음

      
p95LatencyMsms응답 시간 히스토그램의 95 퍼센타일"요청 100개 중 95개는 이 시간 안에 끝남". 느려진 걸 평균보다 잘 드러냄. 판정은 p95가 기준(15분 전 ~ 5분 전)의 2배 이상이면 주의. 구간 경계로 추정해서 근사값

      
series[].atUTC30초 간격각 점의 값은 그 시각 기준 최근 1분 값

    { "at": "2026-10-01T06:55:38Z", "requestsPerMinute": 1.6, "errorRate": 1.0, "avgLatencyMs": 3.0, "p95LatencyMs": 4.75 }

GET/api/apps/{app}/pods구현 · MON-06 · LOG-09

    
앱 파드마다 상태를 돌려줍니다. 재시작 · CrashLoopBackOff · OOMKilled 같은 쿠버네티스 이상 신호도 여기서 봅니다.

    

      
필드타입뜻

      
name문자열파드 이름

      
phase문자열Pending · Running · Succeeded · Failed · Unknown

      
readyboolean트래픽을 받을 준비가 됐는지 (readiness 통과). Running이어도 false일 수 있습니다

      
restarts숫자컨테이너 재시작 횟수. 늘어나면 앱이 죽었다 살아나는 중

      
slot / image문자열슬롯(색 · track)과 이미지 버전

      
node / startedAt문자열 / UTC떠 있는 서버, 시작 시각

      
problem문자열 | null지금 문제: CrashLoopBackOff(계속 죽음), ImagePullBackOff · ErrImagePull(이미지 못 받음), CreateContainerConfigError(설정 오류)

      
lastRestartReason문자열 | null마지막 재시작 이유: OOMKilled(메모리 초과), Error(앱 비정상 종료)

      
cpuMillicores숫자 | nullCPU 사용량. 1000 = 1코어. metrics-server 값이 없으면 null

      
memoryMiB숫자 | null메모리 사용량 (MiB)

다른 앱 지원 범위

    
lily-cicd로 배포한 앱이면 언어 · 프레임워크와 상관없이 됩니다. 앱 코드에 추가할 것은 없습니다.

위험도 기준

    
패널 상태(/status)와 앞으로의 자동 판정이 같은 기준을 씁니다. 기준값은 환경변수 JUDGE_*로 바꿀 수 있습니다.

    

      
위험도조건 (최근 1분)색조치

      
보류 (-1)요청 < 20회/분gray판정하지 않음

      
정상 (0)에러율 < 1%green없음

      
알림 (1)에러율 ≥ 1%green기록

      
주의 (2)에러율 ≥ 2%, 또는 p95 응답 시간이 기준(15분 전 ~ 5분 전)의 2배 이상yellow주의 알림

      
위험 (3)에러율 ≥ 5%red롤백 권장 (자동 롤백은 cicd 역할 합의 후)
