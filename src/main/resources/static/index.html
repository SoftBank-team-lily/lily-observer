lily-observer API

배포된 앱의 요청 지표와 로그를 조회합니다. 대시보드와 AI 진단이 이 API를 씁니다.

개요 인증 지표 조회 로그 조회 위험도 기준 에러 응답 예정 API

개요

[사용자 요청] → ingress-nginx (앱마다 {app}-ingress) → Prometheus ─┐
[앱 로그]     → Fluent Bit (서버마다 1개)  → CloudWatch Logs ──┤
                                                               ▼
                                         lily-observer  /api/apps/{app}/...
  • 지표는 앱이 아니라 입구(ingress-nginx)에서 셉니다. 앱 언어 · 프레임워크와 상관없이 같은 숫자가 나옵니다.
  • 앱은 {app}-ingress 이름으로 구분합니다 (lily-cicd 규칙). 블루그린의 blue · green은 지표에서 구분하지 않습니다.
  • 로그는 /lily/apps 로그 그룹, 파드마다 스트림 {namespace}.{app}.{pod}에 7일 보관됩니다.
  • Prometheus 보관은 1일입니다. 지표 조회 구간은 최대 6시간입니다.

인증

/api/**는 헤더 Authorization: Bearer {OBSERVABILITY_API_TOKEN}이 필요합니다. 서버에 토큰이 설정되지 않았으면 인증이 꺼져 있습니다 (로컬 실행 전용).

GET/api/apps/{app}/metrics구현

앱의 최근 1분 요청 지표(카드용)와 30초 간격 추이(그래프용)를 돌려줍니다.

요청 파라미터

이름위치기본값설명
app경로-앱 이름. 소문자 · 숫자 · -. 배포할 때 쓴 이름 그대로 (예: lily-test)
namespace쿼리default앱이 배포된 네임스페이스
window쿼리10m추이 구간. 30s, 10m, 1h 형식. 1분보다 짧으면 1분, 6시간보다 길면 6시간으로 맞춥니다

응답 필드

필드타입 · 단위뜻
app, namespace문자열요청한 값 그대로
current객체지금 시각 기준 최근 1분 요약. 대시보드 카드에 씁니다
series배열window 구간을 30초 간격으로 나눈 점들. 각 점의 값은 그 시각 기준 최근 1분 값입니다. 그래프에 씁니다
series[].at시각 (UTC, ISO-8601)그 점의 기준 시각. 한국 시간은 +9시간

지표 하나하나

지표단위계산 방법읽는 법
requestsPerMinute
분당 요청 수		 회/분 ingress-nginx가 센 요청 수의 최근 1분 증가량.
sum(increase(nginx_ingress_controller_requests{ingress="{app}-ingress"}[1m]))		 응답 코드와 상관없이 모든 요청. 소수점이 나오는 건 Prometheus가 15초 간격 숫자로 1분 값을 추정하기 때문입니다. 20 미만이면 위험도 판정을 보류합니다 (적은 요청으로 비율이 크게 튀는 걸 막기 위해)
errorRate
에러율		 0.0 ~ 1.0 5xx 응답 수 ÷ 전체 요청 수 (최근 1분).
status=~"5.."인 요청만 에러로 셉니다		 0.05 = 5%. 4xx(잘못된 주소, 권한 없음 등)는 사용자 쪽 문제라 에러로 세지 않습니다. 요청이 없으면 0. 위험도 기준: 1% 알림 · 2% 주의 · 5% 위험
avgLatencyMs
평균 응답 시간		 밀리초 ingress-nginx가 요청을 받은 순간부터 응답을 다 보낼 때까지 걸린 시간의 평균.
request_duration_seconds_sum ÷ _count (최근 1분)		 앱 처리 시간 + ingress와 앱 사이 전달 시간. 평균이라 느린 요청 몇 개는 묻힐 수 있습니다. 위험도 기준: 배포 전보다 2배 이상이면 주의

주의: 지표는 입구를 지나는 요청만 셉니다. 쿠버네티스가 직접 보내는 상태 확인(health probe)은 입구를 지나지 않아 빠집니다. 요청이 한 번도 없던 앱은 current가 모두 0, series가 비어 있습니다.

응답 예시

{
  "app": "lily-test",
  "namespace": "default",
  "current": { "requestsPerMinute": 42.0, "errorRate": 0.024, "avgLatencyMs": 18.0 },
  "series": [
    { "at": "2026-10-01T06:22:03Z", "requestsPerMinute": 4.0, "errorRate": 1.0, "avgLatencyMs": 3.3 },
    { "at": "2026-10-01T06:22:33Z", "requestsPerMinute": 4.0, "errorRate": 1.0, "avgLatencyMs": 3.3 }
  ]
}

GET/api/apps/{app}/logs구현

    
CloudWatch Logs에서 그 앱의 최근 로그를 돌려줍니다. 줄마다 어느 파드 · 슬롯 · 이미지 버전에서 나온 로그인지 붙어 있어 어떤 배포에서 난 로그인지 바로 보입니다.


    
요청 파라미터

    

      
이름위치기본값설명

      
app경로-앱 이름

      
namespace쿼리default앱 네임스페이스

      
since쿼리15m얼마 전부터. 15m, 1h, 2d 형식. 최대 7일 (CloudWatch 보관 기간)

      
level쿼리allerror면 ERROR · Exception · Error · panic · Traceback 중 하나가 들어간 줄만 (대소문자 구분)

      
limit쿼리100최근 것부터 최대 개수 (1 ~ 500). 결과는 오래된 순으로 정렬

    


    
응답 필드 (배열의 각 항목)

    

      
필드타입뜻

      
at시각 (UTC)앱이 로그를 찍은 시각 (컨테이너 로그 파일 기준)

      
pod문자열로그를 찍은 파드. 예: lily-test-green-7bfdd46749-7hm67

      
slot문자열 | nulllily-cicd 슬롯 라벨. 카나리면 stable · canary, 블루그린이면 blue · green. 둘 다 있으면 카나리 값

      
image문자열 | null이미지 이름:태그 (레지스트리 주소 제외). 예: lily-test:20261001-053104. 태그가 배포 시각이라 몇 번째 배포인지 알 수 있습니다

      
message문자열앱이 찍은 로그 한 줄 그대로

    

    
알려진 제한: 여러 줄짜리 에러(Java 스택 트레이스의 at ... 줄)는 줄마다 따로 저장됩니다. 에러 위치를 보려면 같은 시각 앞뒤 로그를 level=all로 함께 조회하세요. 이 API를 쓰려면 서버 IAM 역할에 logs:FilterLogEvents 권한이 필요합니다.


    
응답 예시


[
  {
    "at": "2026-10-01T06:22:49.953Z",
    "pod": "lily-test-green-7bfdd46749-7hm67",
    "slot": "green",
    "image": "lily-test:20261001-053104",
    "message": "java.lang.IllegalStateException: chaos: forced application error"
  }
]

위험도 기준

    
위 지표로 판정합니다 (판정 루프는 lily-cicd와 역할 합의 후 진행). 기준값은 환경변수 JUDGE_*로 바꿀 수 있습니다.

    

      
위험도조건 (최근 1분)조치

      
보류requestsPerMinute < 20판정하지 않음

      
0 정상errorRate < 1%없음

      
1 알림errorRate ≥ 1%기록

      
2 주의errorRate ≥ 2%, 또는 avgLatencyMs가 배포 전의 2배 이상주의 알림

      
3 위험errorRate ≥ 5%자동 롤백 (lily-cicd 롤백 API)

    

    
같은 등급이 연속 2번 나와야 조치합니다 (순간 스파이크 무시).
